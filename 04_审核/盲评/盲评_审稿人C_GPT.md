## 评审口径

“通过”表示按当前卡片描述满足门槛。“不通过”表示当前定义下存在硬伤。“不确定”表示材料不足，按硬门槛暂不算通过。

### C01 个人金融智能体的执行权限网关

- H1 不通过。核心抽象是通用智能体执行授权网关，去掉金融后仍可用于企业采购、客服退款等高风险动作。
- H2 通过。使用者是开发个人金融智能体的程序员，每次付款、退款或交易都涉及放行决策。
- H3 通过。可以和平台原生控制比较越权、重复扣款、错误重试和误拦率。
- H4 通过。属于执行安全基础设施，不属于已否决类型。
- H5 通过。Stripe、PayPal 沙箱、Alpaca 模拟盘和自建故障集足以支持原型。
- H6 不通过。材料没有已承诺试用的外部开发者，开源项目的真实接入和持续使用仍未证明。

1. **现有工具能否完成同一任务？**  
   能完成相当一部分。Coinbase 已有单笔和会话限额，AP2 已有可验证授权凭证和交易护栏，通用 Guardrails 也能控制工具调用。公开产品未必覆盖跨支付渠道的超时状态确认和统一幂等处理，但开发者可以组合现有能力。[coinbase.com](https://www.coinbase.com/developer-platform/products/agentic-wallets?utm_source=chatgpt.com)

2. **如何证明有用？**  
   用同一攻击和故障测试集，对比平台原生控制、原生控制加本网关，测越权执行、重复扣款、错误重试、漏拦和误拦。

3. **谁会回来用第二次？**  
   接入多个资金工具的智能体开发者会在每次动作执行时调用它。前提是集成成本低于自行组合 AP2、平台限额和幂等逻辑的成本。

4. **面试价值**  
   能展示 API 集成、权限模型、威胁建模、幂等设计、故障恢复和安全测试。对银行、支付、互联网平台金融科技岗位较有价值，对保险和财富管理岗位的直接关联较弱。

5. **三个月能否做出可演示版本？**  
   能做出沙箱演示。最难的一步是定义不同支付和交易渠道的真实状态语义，并证明重试不会造成重复资金动作。

- **最大风险**  
  现有协议和平台控制快速完善后，本网关可能只剩集成层价值，且开发者采用难以验证。

### C03 中文交易意图到条件单的安全编译器

- H1 不通过。去掉金融后仍可成为通用自然语言动作编译器，金融并非技术方案不可替代的组成部分。
- H2 通过。使用者是个人投资者，决策是确认、修改或拒绝条件单。
- H3 通过。字段错误、应追问却猜测、过度拒绝都可以建立测试集比较。
- H4 通过。不是荐股，重点是订单表达和执行安全。
- H5 通过。Alpaca 模拟盘和自建中文歧义集可以支持原型。
- H6 通过。项目负责人本人即可使用，也可招募有模拟交易经验的同学。

1. **现有工具能否完成同一任务？**  
   能。IBKR IBot 已支持自然语言创建复杂订单和算法订单，并允许提交前修改和确认。本网关的差异只能建立在“歧义时追问”的系统评测上。[Interactive Brokers LLC](https://www.interactivebrokers.com/en/trading/ibot.php?utm_source=chatgpt.com)

2. **如何证明有用？**  
   使用相同输入，对比强模型加券商原生工具和本网关，分别统计字段错误、擅自补全、该追问却下单、无必要拒绝四类结果。

3. **谁会回来用第二次？**  
   经常设置条件单、分批卖出或复杂期权单的交易者会重复使用。普通投资者使用频率可能不足以形成持续产品。

4. **面试价值**  
   能展示中文语义解析、结构化输出、约束校验、澄清式交互和模拟交易 API。主要覆盖证券和智能体岗位，与银行支付、保险岗位的迁移性有限，也和已有 perquant 重叠。

5. **三个月能否做出可演示版本？**  
   能。最难的是构造覆盖真实歧义的中文测试集，并把“没有唯一正确订单”转化为稳定的追问策略。

- **最大风险**  
  这是已有证券项目的延伸，且 IBot 等产品已经完成了自然语言订单的主要流程。

### C04 小商户多渠道收款对账与差错处理

- H1 通过。支付订单、渠道结算和银行入账之间的状态语义属于资金清算问题，跨系统匹配和异常处理是技术核心。
- H2 通过。使用者是小商户老板或兼职财务，每天决定追查哪些差错。
- H3 通过。可以比较差错定位时间、漏报率、误报率和第二天继续导入的比例。
- H4 通过。核心是跨系统结算对账和差错闭环，不是普通记账。
- H5 通过。支付沙箱、账单规则合成和少量真实商户数据可以重建流程。
- H6 不通过。材料只有招募计划，没有已确定试用的小商户。

1. **现有工具能否完成同一任务？**  
   能。Hyperswitch 已公开支持商户、支付服务商和银行之间的三方对账，Excel、聚合收款后台和 Ping++ 也能完成部分任务。是否有面向小商户的免费自助版本，公开证据仍不充分。[Juspay Hyperswitch](https://hyperswitch.io/reconciliation?utm_source=chatgpt.com)

2. **如何证明有用？**  
   让同一商户用现有 Excel 或后台和本网关各处理一周账单，比较定位时间、漏报、误报，以及“文件未到、无业务、已结算未入账”分类准确率。

3. **谁会回来用第二次？**  
   每天或每周结算的小商户、兼职财务和电商经营者会重复导入账单。准确率和导入便利性决定留存。

4. **面试价值**  
   能展示数据清洗、跨系统键匹配、状态机、异常队列、文件处理和商户流程理解。对银行运营、支付、清算、互联网平台岗位覆盖面最广。

5. **三个月能否做出可演示版本？**  
   能。最难的是获取一个真实商户，并处理各渠道账单字段、退款、部分到账和延迟结算的差异。

- **最大风险**  
  如果没有真实商户持续导入，项目很容易退化成带界面的 Excel 自动化。

### C08 保险条款赔付计算与初审分流

- H1 通过。保险责任、免责、等待期、免赔额和赔付比例构成金融合同规则，规则执行与证据不足分流都依赖技术。
- H2 通过。有保单的个人和家庭在出险后会作出是否申请、补什么材料的决策。
- H3 通过。事实给定时测金额计算正确率，事实有争议时测是否正确转人工和列出缺失材料。
- H4 通过。它是条款规则执行和初审分流，不是普通报告生成。
- H5 通过。公开条款、判例、合成理赔事实和少量自愿保单可以支持单一险种原型。
- H6 通过。亲友中较容易找到有保单或有理赔经历的试用者，但应限定为辅助判断。

1. **现有工具能否完成同一任务？**  
   部分能。openIMIS 已支持保险产品配置、理赔提交、规则筛查和理赔审核，但主要面向保险计划运营方。通用大模型也能直接阅读条款。面向个人的公开赔付计算工具是否普遍存在，不确定。[openIMIS](https://openimis.org/health-insurance?utm_source=chatgpt.com)

2. **如何证明有用？**  
   建立人工标注案例，分别比较金额计算准确率、条款定位准确率、事实不足时的补证建议，以及错误地给出确定结论的比例。

3. **谁会回来用第二次？**  
   用户通常只在出险时使用，复用频率低。保险经纪人、家庭财务管理者或经常处理理赔的人更可能重复使用。

4. **面试价值**  
   能展示 RAG、规则引擎、版本管理、结构化抽取、不确定性处理和人机协作。对保险科技、银行运营、风控和知识工程岗位都有一定迁移性。

5. **三个月能否做出可演示版本？**  
   能，但必须只选一个险种和有限条款版本。最难的是条款版本控制和为“事实争议”建立可靠的人工金标准。

- **最大风险**  
  正常赔案的真实结果数据难获得，条款版本差异也会迅速削弱结论可靠性。

### C15 老人转账前防诈助手

- H1 通过。转账资金动作、收款人风险和家属授权通知构成金融安全决策，语音交互和识别技术直接影响执行。
- H2 通过。使用者是老年人和家属，决策发生在每次转账前。
- H3 不通过。公开分类数据可以测文本识别，但“仅凭交易信息是否应拦截”和真实诈骗场景缺乏稳定金标准。
- H4 通过。属于反诈和适老化金融服务。
- H5 通过。公开 TeleAntiFraud 数据、合成语音和情景脚本可支持原型。
- H6 不通过。材料没有证明老人愿意在多次真实转账咨询中持续使用。

1. **现有工具能否完成同一任务？**  
   能完成部分任务。银行已有亲情确认、语音转账和适老化功能，反诈系统也能做风险识别。是否已有把对话理解、转账前询问和家属授权完整合并的公开产品，不确定。

2. **如何证明有用？**  
   分别测正常转账误拦率、已知诈骗话术召回率、老人从误拦中恢复的成功率，以及家属通知的准确率。不能只用公开文本分类准确率证明产品有效。

3. **谁会回来用第二次？**  
   老人可能在每次不熟悉的收款人转账前使用，家属可能在风险事件出现时查看。过多误拦或复杂语音流程会迅速降低复用。

4. **面试价值**  
   能展示语音交互、文本分类、异常检测、无障碍设计、风险分层和人机协作。对银行、支付、普惠金融和反诈岗位有明显关联，对保险和财富管理覆盖较弱。

5. **三个月能否做出可演示版本？**  
   能做出语音问答和模拟风险提示。最难的是在信息极少时减少误报，并让老人真正理解和接受提示。

- **最大风险**  
  转账前通常拿不到完整诈骗通话上下文，系统可能既拦不住诈骗，又打扰大量正常转账。

### C17 个人征信报告解读与异议助手

- H1 通过。征信记录、信贷审批和异议流程属于金融规则，报告解析、风险标注和材料准备依赖技术。
- H2 通过。准备申请房贷或车贷的个人会作出申请时机和是否提出异议的决定。
- H3 通过但需收窄。可以测字段识别、关键记录召回、异议材料完整性，不能把房贷最终获批作为唯一指标。
- H4 不通过。当前核心输出是报告解读、可疑记录标注和材料生成，接近已否决的报告生成、金融核验边界。
- H5 通过。报告格式可合成，本人或家人自愿样本可在本地处理。
- H6 不通过。真实报告高度敏感，材料没有证明能找到愿意多次使用并分享反馈的用户。

1. **现有工具能否完成同一任务？**  
   官方渠道已经提供个人信用报告查询，银行也提供查询服务。征信管理规则要求对专业名词进行解释，并允许信息主体提出异议。具体是否已有成熟的公开端到端解读服务，不确定。[pbccrc.org.cn](https://www.pbccrc.org.cn/zxfw/gr/cx/20241029/6bb3ada5b92641779ee33e06c30f1e4c.html?utm_source=chatgpt.com)

2. **如何证明有用？**  
   做匿名盲测，比较关键记录识别率、可疑账户召回率、异议材料完整性和流程错误率。不要把“最终获贷”作为短期实验结果。

3. **谁会回来用第二次？**  
   主要是申请贷款前、报告更新后或发现异常时使用，通常是低频需求。

4. **面试价值**  
   能展示文档解析、隐私保护、合规流程、字段抽取和信贷场景理解。对征信、信贷风控和银行科技岗位有价值，支付和保险关联较弱。

5. **三个月能否做出可演示版本？**  
   能做出本地处理的合成报告原型。最难的是隐私管理和证明标注结果确实能改善异议处理，而不是只生成更易读的报告。

- **最大风险**  
  产品边界很难与已排除的报告解读、核验和材料生成工具区分。

### C18 多笔分期与消费信贷的真实成本和还款规划

- H1 通过。分期手续费、实际年化成本、本金占用和提前还款规则是金融合同问题，持续跟踪和动态再规划是技术闭环。
- H2 通过。有多笔分期的年轻人会决定还款顺序、是否提前还款和是否停止新增分期。
- H3 通过。可比较年化成本误差、总利息预测误差、现金流违约次数和用户执行率。
- H4 通过，附条件。MVP必须包含动态现金流约束、执行跟踪和再规划，只做截图计算和排序就应改判不通过。
- H5 通过。本人和同学账单、截图、平台规则和合成账单足以支持原型。
- H6 通过。项目负责人和同学容易成为首批用户，账单更新具有月度重复性。

1. **现有工具能否完成同一任务？**  
   单个平台的账单、年化展示和通用计算器可以完成局部任务，大模型也能直接读截图。跨平台合并、现金流约束和持续跟踪未见明确的统一公开方案。人民银行已规定贷款年化利率应计入相关费用，并可按内部收益率法计算，为评测提供了客观口径。[lincang.gov.cn](https://lincang.gov.cn/file/lcoldData/_local/7/99/DF/B1AA1155F5B9BABCB25FC7CCFC0_FA063539_3332E.pdf?utm_source=chatgpt.com)

2. **如何证明有用？**  
   先用合同现金流计算真实年化和总成本，再与平台展示、通用大模型和“先还利率最高”基线比较，随后观察用户是否按计划执行、下月是否继续更新。

3. **谁会回来用第二次？**  
   有多笔账单的人会在每月账单生成或发薪日前回来查看，现金流变化时需要重新规划。

4. **面试价值**  
   能展示金融数学、现金流建模、OCR、产品交互、行为跟踪和消费金融理解。对消费金融、支付、银行零售和互联网金融产品岗位较有帮助，对保险岗位关联较弱。

5. **三个月能否做出可演示版本？**  
   能。最难的是正确处理手续费、分期偿还本金、提前还款费用和不同平台的规则，并让用户持续更新数据。

- **最大风险**  
  如果没有动态跟踪和执行反馈，项目会退化成已被否决的静态金融计算器。

## 进入下一阶段实测的卡片

我会让以下四张进入实测，但都先设置一个明确的用户验证门槛。

- **C04**。最接近真实支付运营工作，结果指标清楚，商户每日或每周有重复需求。先拿到至少一名小商户连续一周导入真实或脱敏账单。
- **C08**。保险条款规则和事实不足分流能形成可解释的客观评测，亲友保单足以启动小规模试用。先限定一个险种和一个条款版本。
- **C15**。反诈、适老化和金融安全的面试辨识度高，功能可以快速做出。先验证三名老人是否愿意完成多次正常转账咨询，并记录误拦后的恢复情况。
- **C18**。用户容易招募，账单按月重复，能够持续迭代。先证明动态再规划和执行跟踪带来的效果超过单次计算器。
