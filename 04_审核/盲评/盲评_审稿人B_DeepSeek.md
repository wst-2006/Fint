## C01 个人金融智能体的执行权限网关

**H1–H6**

| 门槛 | 判定 | 理由 |
|---|---|---|
| H1 | **通过** | 去掉“金融动作的授权与状态核验”，只剩通用 API 网关或 guardrails；去掉“智能体执行”，金融场景本身不成立。两端都不可删。 |
| H2 | **通过** | 使用者是“开发个人金融智能体的程序员”，具名到角色，决策对象是每次资金动作的放行/拦截/确认，属于重复且单次错误的代价明确的决策。 |
| H3 | **通过** | 可与“平台原生控制全部开启”做对照，指标是越权执行、重复扣款、错误重试和误拦率，客观且可复现。 |
| H4 | **通过** | 不属于第二节任何否决类型。 |
| H5 | **通过** | Stripe、PayPal、Alpaca 沙箱公开可用，测试集可自建。 |
| H6 | **通过** | 目标使用者是开发者，负责人本身具备 API 与 Git 能力，通过开源仓库可以直接接触早期开发者。原型阶段找到“亲自用起来”的开发者是可行的，虽然不保证。 |

**问题 1：现有工具能否完成同一任务？**

不能完全完成，但差距正在收窄，且收窄速度很快。AP2 的 Intent Mandate 已经包含 spend caps、time windows、merchant restrictions 和 instant revocation，每笔交易对约束的校验在毫秒级。Coinbase Agentic Wallets 提供 per-session 和 per-transaction 的可编程限额，并强调私钥不进入模型上下文。C01 卡中“平台原生控制全部开启”这一对照条件，在 AP2 + Coinbase 的组合下，已经覆盖了“额度、次数、有效期、商户限制”这几个核心维度。

C01 真正的增量在 AP2 和 Agentic Wallets **没有明确覆盖**的两件事：（1）**外部文本中的注入指令隔离**；（2）**超时后“查清渠道实际状态再决定是否重试”**。前者是 LLM 应用层安全问题，后者是支付渠道状态机的正确性问题。如果 C01 把自己定义为“AP2 之上、针对注入和超时状态不确定性的补充层”，它还有位置；如果把自己定义为“智能体支付的权限网关”整体，AP2 和 Coinbase 已经是更强的 incumbent。

**问题 2：能用什么可独立核验的结果证明有用？**

可以。攻击与故障测试集上的三类错误计数（越权执行、重复扣款、超时错误重试）+ 误拦率，是一个独立可复现的 benchmark。更强的信号是 **有外部开发者把 C01 作为依赖引入一个非玩具的智能体项目**，并在 issue 或 PR 中留下使用记录。前者是“证明自己不比现状差”，后者才是“证明有人需要它”。

**问题 3：谁会回来用第二次？凭什么？**

开发个人金融智能体、且**不信任单一平台原生控制**的开发者。回来的理由只能是：C01 在注入和超时重试两个维度上提供了平台没有的覆盖，并且接入成本低于自己写。如果接入成本接近自己写 200 行 guardrails，没有人会回来。

**问题 4：面试价值**

展示的是**支付系统正确性思维**（状态机、幂等、超时补偿）和**LLM 应用安全**（注入隔离），这两者在银行、支付、互联网平台金融科技岗位中都是硬信号。覆盖面中等偏上，但岗位方向集中在“支付/平台工程”，对保险、财富管理覆盖较弱。

**问题 5：三个月能否做出可演示、可让真实用户试用的版本？最难的一步是什么？**

技术上可以。最难的一步不是代码，是**证明“平台原生控制全部开启”确实不够用**。如果测试集设计得不够刁钻，对照结果会是“无差别”，项目在评审桌上会立刻被推翻。需要把测试集的构建本身当作核心交付物来对待。

**最大风险**：AP2 在 FIDO 标准化之后，生态可能在 6–12 个月内把“注入隔离 + 超时状态核验”也纳入平台层，C01 的窗口期很短。

## C03 中文交易意图到条件单的安全编译器

**H1–H6**

| 门槛 | 判定 | 理由 |
|---|---|---|
| H1 | **通过** | 去掉“中文意图解析与歧义追问”，只剩订单校验；去掉“交易执行”，只是一个 NLP demo。两端都必要。 |
| H2 | **通过（勉强）** | 使用者是负责人本人，真实但单一；决策是“确认或修改条件单”，对个人投资者是重复决策。H2 要求“具名使用者”，本人算，但“面对重复或高价值的金融决策”在模拟盘语境下价值有限。判通过，但弱。 |
| H3 | **通过** | 字段错误、该追问却下单、拒绝过多三类错误可分开计数，可与强模型 + 券商原生工具对照。 |
| H4 | **通过** | 条件单不是“以 A 股选股或交易收益为主要产出”，不属于否决类型。 |
| H5 | **通过** | Alpaca 模拟盘和自建测试集可获取。 |
| H6 | **通过（弱）** | 本人是真实使用者，但“亲自用起来”在模拟盘上只完成了一半；要让第二个人用，仍然依赖模拟盘，国内券商接口不可得。 |

**问题 1：现有工具能否完成同一任务？**

盈透 IBot 已经能自然语言生成复杂订单并让用户修改提交，华泰 AI 涨乐和 Alpaca MCP 也在同一方向。C03 的差异化命题是“**歧义时正确追问，而不是猜**”。这是一个真实且重要的产品问题，但它是否构成一个独立项目的空间，取决于一个可检验的经验判断：**现有强模型 + 券商工具在中文歧义条件单上是否已经在系统地追问？** 如果答案是“偶尔追问但经常猜”，C03 有价值；如果答案是“已经普遍追问”，C03 被推翻条件直接触发。候选卡自己也把这一点设为推翻条件，说明负责人清楚这是命门。

更棘手的是 H4 与 perquant 的关系。C03 的“执行”端是模拟盘条件单，但它服务的决策对象与 perquant 同属证券交易领域。盲评包要求“第二个项目要在类型上明显不同”，C03 在**问题类型**上（意图编译 vs 策略执行）确实不同，但在**领域标签**上很容易被面试官归入“又一个证券交易项目”。这不是硬门槛问题，是定位风险。

**问题 2：能用什么可独立核验的结果证明有用？**

歧义测试集上“该追问却擅自下单”的错误率下降，是一个干净的客观指标。但需要注意：这个指标的说服力高度依赖测试集的质量。如果测试集是自建的，且规模有限，外部审稿人会质疑“你是不是挑了自己擅长的歧义类型”。

**问题 3：谁会回来用第二次？凭什么？**

短期内只有负责人本人。第二个人需要同时满足“有模拟盘账户”“愿意用中文输入条件单”“遇到过歧义并觉得追问有价值”三个条件，这个交集在负责人可触达的范围内可能很小。

**问题 4：面试价值**

展示的是**NLP 在金融约束下的产品判断**（知道什么时候该追问）和**测试集设计能力**。对智能投顾、智能体岗位有信号。但覆盖面窄，且容易被“IBot 已经做了”一句话压制。

**问题 5：三个月能否做出可演示、可让真实用户试用的版本？最难的一步是什么？**

技术上可以。最难的一步是**说服第二个真实用户用起来**。负责人本人是天然使用者，但单人使用不能证明“有真实使用者”的 H2 在面试叙事中的分量。如果找不到第二个模拟盘用户，C03 的演示会退化为“我自己用着挺好”的项目。

**最大风险**：歧义测试集的设计质量不足以证明现有产品“在猜”，或者现有产品实际上已经普遍追问，导致项目的前提被公开证据推翻。

## C04 小商户多渠道收款对账与差错处理

**H1–H6**

| 门槛 | 判定 | 理由 |
|---|---|---|
| H1 | **通过** | 去掉“三方对账与差错状态分类”，只剩账单导入；去掉“小商户多渠道收款”，对账对象不存在。两端都成立。 |
| H2 | **通过** | 小商户老板/兼职财务是具名使用者，每日决定追哪些差错，重复且直接影响现金流。 |
| H3 | **通过** | 可与“商户现在用的 Excel 或聚合收款后台”比较差错定位时间和漏报，客观可测。 |
| H4 | **通过** | 不属于第二节否决类型。不是记账，是对账与差错处理，决策对象不同。 |
| H5 | **通过** | 支付沙箱、按微信/支付宝规则合成、真实小店均可获取。 |
| H6 | **通过（有条件）** | 负责人可以接触小商户，但“招募到愿意持续导入数据的真实小店”不是自动成立的。判通过，因为门槛只要求“能找到”，不要求“已找到”。 |

**问题 1：现有工具能否完成同一任务？**

这是 C04 最需要正视的问题。候选卡说“未找到小商户可免费自助完成三方对账的证据”，但公开信息并不支持这个判断的强版本。用友畅捷通明确以“永久免费使用”提供微信、支付宝、银联、对公账户统一接入和“智能自动对账，自动匹配订单与收款记录，支持批量核销与异常提醒”。农信易扫也以“免费提供对账平台”面向小微商户，支持全渠道交易明细查询和报表导出。这些产品未必把“文件未到 / 当天无业务 / 渠道已结算银行未入账”这三类状态的语义区分做到位，但它们在“多通道接入 + 自动匹配 + 异常标记”这个层面已经覆盖了 C04 的大部分表层功能。

C04 的差异化必须精确地落在**差错状态的语义分类**和**大模型驱动的差错解释/沟通话术**上，而不是“我做了一个对账工具”。如果演示中大部分时间在展示“导入三个文件、匹配、输出差异”，评审会立刻问：“用友免费版不就有吗？”负责人需要能在 30 秒内回答清楚：**用友免费版对“渠道已结算但银行未入账”和“文件未到”的处理是什么，C04 多做了什么。**

**问题 2：能用什么可独立核验的结果证明有用？**

“差错定位时间缩短”和“漏报率下降”是两个好指标，但需要商户**愿意提供当前的 Excel 和对账结果作为 baseline**。如果商户只愿意说“感觉快了”，证据强度会大打折扣。最强的信号是**商户第二天继续导入**，这是一个行为指标，比任何问卷都硬。

**问题 3：谁会回来用第二次？凭什么？**

小商户老板或兼职财务，前提是 C04 嵌入了他**已有的每日/每周对账动作**，而不是增加一个新动作。如果商户需要额外花时间导出文件、再上传到一个新工具里，回来的概率很低。回来的理由只能是：C04 给出的差错清单比聚合后台更准，且解释了他自己看不懂的“钱去哪了”。

**问题 4：面试价值**

展示的是**金融运营流程理解**（对账、差错、未达账）和**在已有免费工具的压力下做产品差异化的能力**。对银联、支付类岗位、银行运营岗覆盖很好。AI 含量偏低是真实短板，但如果能把“差错语义分类”做成可复用的规则/模型层，而不是 prompt 堆砌，仍然有工程信号。

**问题 5：三个月能否做出可演示、可让真实用户试用的版本？最难的一步是什么？**

技术上可以，因为核心是结构化对账而非模型能力。最难的一步是**招募到一个愿意暴露真实账单和当前对账方式的小商户**。这不是技术问题，是信任和隐私问题。如果找不到，C04 的推翻条件直接触发。

**最大风险**：免费聚合收款/财务工具已经覆盖了“多通道自动匹配”，C04 如果不能在差错语义分类上做出可演示的显著增量，会被归入“Excel 自动化”而非“金融科技产品”。

## C08 保险条款赔付计算与初审分流

**H1–H6**

| 门槛 | 判定 | 理由 |
|---|---|---|
| H1 | **通过** | 去掉“条款解析成可执行规则”，只剩保险知识问答；去掉“赔付计算与分流”，规则引擎没有对象。两端都必要。 |
| H2 | **通过** | 有保单的个人/家庭，出险后判断“能赔多少、材料是否齐、是否值得申请”，是低频但单次价值极高的金融决策。 |
| H3 | **通过** | 事实给定时计算正确率可与强通用 AI 直接读条款对照；争议案例中“是否正确转人工”也可独立判定。 |
| H4 | **通过** | 不是报告生成，也不是核验/事实链；输出是金额和分流判断，决策对象明确。 |
| H5 | **通过（有条件）** | 行业协会条款库和公开判例可获取；家人朋友的保单和理赔经历是有限但真实的补充。条款版本繁多是工程负担，不是不可获取。 |
| H6 | **通过** | 负责人可以通过家人、朋友的真实保单和理赔场景获得第一批使用者。保险是“身边总有人出过险”的领域，接触成本低于 C04 的小商户。 |

**问题 1：现有工具能否完成同一任务？**

公开市场上面向个人的“条款计算 + 证据不足分流”工具确实不显著。已有的“AI 保险顾问”和“保险金计算”类 skill 更多是保费测算、产品对比或通用赔付估算，而不是“把一款具体百万医疗险的条款解析成可执行规则，事实给定时算出金额并定位原文，事实不清时输出补什么证据”。openIMIS 是机构端配置工具，不是个人自助工具。这个缝隙是真实的。

但需要区分两件事：**计算正确率**和**分流判断**。强通用 AI 直接读条款，在“责任清晰、事实完整”的案例上，计算正确率可能已经很高。C08 的增量主要在：（1）**可追溯性**——每一条计算都定位到条款原文；（2）**事实不清时的正确停止**——不强行算出一个数字，而是输出“证据不足，需补充什么”。第二点尤其有价值，因为保险理赔中“算对数、判错案”的根源往往不是计算错误，而是把争议事实当作已定事实来处理。

**问题 2：能用什么可独立核验的结果证明有用？**

计算正确率（对照强通用 AI）和争议案例中的转人工正确率，都是可独立核验的。更强的证据是**有真实用户依据 C08 的输出补充了材料，或决定不申请/申请，并事后被证明这个决定是合理的**。但“事后合理”很难在三个月内闭环，所以面试叙事应该以“计算正确率 + 分流正确率”为主，以个案跟踪为辅。

**问题 3：谁会回来用第二次？凭什么？**

保险赔付是低频事件，同一个人不会每月回来。C08 的“第二次”更可能来自**同一家庭的不同险种/不同成员**，或者**同一个人在不同时间点的理赔进展跟踪**。如果产品设计成一次性查询，H2 的“重复决策”属性就会弱化；如果设计成“材料补充清单可以保存、更新、再核对”，才有回访理由。

**问题 4：面试价值**

展示的是**知识工程 / RAG 在强约束领域的落地能力**（条款结构化、可追溯、证据意识），对平安产险类岗位和保险科技岗位信号很强。覆盖面在保险方向集中，对银行/支付方向一般。如果能把“证据不足时不强行下结论”的产品判断讲清楚，面试官会认为这个本科生具备**受监管领域的产品成熟度**，这在本科生中不常见。

**问题 5：三个月能否做出可演示、可让真实用户试用的版本？最难的一步是什么？**

技术上，把**一个险种、一个条款版本**解析成可执行规则，三个月足够做出可演示版本。最难的一步是**获取足够多的“事实给定”的真实案例来检验计算正确率**。条款库是公开的，判例是公开的，但“真实用户的完整事实 + 真实赔付结果”是稀缺的。如果没有真实结果数据，计算正确率只能用构造案例来测，外部审稿人会质疑构造案例的覆盖度和难度。

**最大风险**：条款版本繁多，如果三个月内只做一个险种的一个版本，演示会显得单薄；如果贪多覆盖多个版本，规则解析的质量会下降，计算正确率被强通用 AI 追平。

## C15 老人转账前防诈助手

**H1–H6**

| 门槛 | 判定 | 理由 |
|---|---|---|
| H1 | **通过** | 去掉“转账前识别诈骗话术和异常收款情形”，只剩语音交互；去掉“老人/视障用户的转账决策”，反诈助手没有特定约束。两端都成立。 |
| H2 | **通过** | 老年人及其家属，转账前决定是否继续，是重复且后果严重的决策。 |
| H3 | **通过（有条件）** | “只有交易信息”和“用户主动提供可疑对话”两种情形下的识别效果可测，误拦后能否自己恢复也可测。但“识别效果”的 ground truth 依赖测试集标注质量。 |
| H4 | **通过** | 不是 AI 投顾体检，不是核验/证据链，不是普通荐股。 |
| H5 | **通过** | TeleAntiFraud 公开数据可用，Apache-2.0。 |
| H6 | **通过** | 负责人可以通过家中老人获得第一批真实使用者。这是 C15 相对 C04 的显著优势：使用者就在身边。 |

**问题 1：现有工具能否完成同一任务？**

竞争比候选卡列出的齐鲁银行亲情安全铃、建行适老服务、微众无障碍版要激烈得多。**云闪付“支付守护”** 已经提供了家庭协作式的交易动态同步、大额交易提醒、高风险操作预警（换设备登录、修改密码）和分级同步阈值，明确覆盖“转账前/转账时让家属知情并介入”的机制。**国家反诈AI** 由公安部刑侦局指导、上海公安研发，已经上线 App 和微信/支付宝小程序，支持语音提问、风险分析、诈骗类型识别和防范建议。这意味着 C15 面对的不只是银行单项功能，而是**一个官方背景、免费、全量触达的通用反诈问答入口 + 一个已在支付 App 内嵌的家庭守护机制**。

C15 的缝隙在于：支付守护解决的是“事后知情和阈值提醒”，国家反诈AI 解决的是“用户主动去问”，而 C15 想做的是 **“转账动作发生前，在转账流程内主动发起一次结构化询问”**。这是一个真实的产品缝隙——老人通常不会在转账前主动打开另一个 App 去问 AI，但他们会在转账时面对一个弹出的“问一问”。问题是，负责人没有银行 App 的嵌入权限，只能做一个独立 App 或小程序，这恰好丢失了“在转账流程内”的位置优势。

**问题 2：能用什么可独立核验的结果证明有用？**

“正常转账咨询的完成率”和“误拦后老人能否自己恢复”是两个好的可用性指标，但它们证明的是“不碍事”，不是“防住了”。防诈效果在三个月内几乎不可能用真实诈骗事件来验证——样本太小，伦理上也难以设计。所以 C15 的证明只能退而求其次：**在标注的诈骗/非诈骗对话集上的分类指标**，加上**老人愿意在真实转账前主动使用的行为数据**。后者比前者更难获得，但也更有说服力。

**问题 3：谁会回来用第二次？凭什么？**

老人回来的前提是**产品足够轻**，轻到不需要“记得打开一个 App”。如果 C15 是一个需要老人主动打开、说出转账信息的独立应用，第二次使用的概率很低。家属回来的前提是**收到有意义的通知**，而不是每次转账都收到一条“一切正常”。C15 的产品形态（独立 App vs 小程序 vs 家属端提醒）比模型本身更决定留存。

**问题 4：面试价值**

展示的是**普惠金融/适老化产品设计**和**在敏感场景下做低摩擦交互**的能力。对银行零售、支付、反诈相关岗位有信号。但面试官如果了解国家反诈AI 和支付守护，会直接问“你和它们有什么不同”，负责人必须有精确的答案，而不是“我集成了语音 + 通知家属”。

**问题 5：三个月能否做出可演示、可让真实用户试用的版本？最难的一步是什么？**

技术上可以。最难的一步是**让老人真的在转账前用它**，而不是在负责人面前演示一次。这需要产品嵌入老人的真实转账习惯，而独立应用天然不占据那个位置。如果 C15 找不到一种“不要求老人改变转账前习惯”的形态，H2 的“真实使用者”会在演示之后迅速流失。

**最大风险**：国家反诈AI + 支付守护的组合已经覆盖了“问”和“家属知情”两端，C15 如果只能在独立 App 里做一个“转账前问一问”，位置劣势可能大于功能增量。

## C17 个人征信报告解读与异议助手

**H1–H6**

| 门槛 | 判定 | 理由 |
|---|---|---|
| H1 | **通过（弱）** | 去掉“征信报告的结构化解读与异议流程映射”，只剩通用文档问答；去掉“征信/信贷决策”，通用文档问答没有特定约束。两端勉强成立，但“金融”端的厚度不如 C08 或 C04。 |
| H2 | **通过（弱）** | 准备申请房贷/车贷的个人，决策是“何时申请、是否异议”，是低频但高价值的决策。问题在于“重复”属性弱：同一个人不会反复解读征信报告。 |
| H3 | **通过** | 可与强通用 AI 直接读报告对照关键记录识别正确率；“是否有人据此提出异议并得到更正”是更强的结果，但三个月内难以积累。 |
| H4 | **不通过** | 候选卡自己标注“接近已否决的报告生成和核验类型”，这是诚实的。C17 的核心输出是“解读报告 + 标出记录 + 生成异议材料清单”，在类型上更接近 **报告生成** 与 **事实核验/证据链** 的混合体，而不是一个独立的金融决策系统。异议流程映射是流程知识，不是金融计算或判断。盲评包明确否决“报告生成”和“核验/证据链类工具”，C17 不能因为加了“征信”标签就绕过这条线。 |
| H5 | **通过（有条件）** | 本人和家人报告可获取，合成样本可构造。但真实样本隐私敏感，数量受限。 |
| H6 | **通过（弱）** | 负责人本人和家人是第一批使用者，但征信报告解读的“真实使用”在家人之间也很敏感，持续使用意愿存疑。 |

**H4 不通过是 C17 的致命问题。** 即便 H1–H3、H5–H6 勉强成立，H4 是否决类型判定，不是“弱通过”可以挽救的。候选卡自己的推翻条件已经写得很清楚：“或盲评认定属于否决类型”。作为盲评审稿人，我认定它属于。

补充的公开信息进一步削弱了 C17 的差异化：即融AI、征信管家、贷查查等产品已经提供人行征信报告 AI 解析、负债结构识别、查询次数分析，甚至异议相关的信贷产品匹配。C17 的“已知对手”栏写“待 GPT 查”，而公开市场上同功能产品并不稀缺。异议流程本身是公开的官方流程，人民银行征信中心互联网平台支持全流程在线异议申请，建设银行等机构也公布了线上异议入口。C17 生成“材料清单”的增量，很难撑起一个独立项目。

**问题 1–3（简要，因 H4 已不通过）**

现有工具在“解读”端已经存在；异议流程是公开标准流程。C17 的可证明结果（关键记录识别正确率）与强通用 AI 的差距可能不足以构成产品。回来用第二次的理由在低频征信场景下尤其薄弱。

**问题 4：面试价值**

如果做成，展示的是 RAG/文档结构化能力，但“报告生成/核验”的标签会在面试中引发“这和已否决类型有什么区别”的追问，而 C17 很难给出一个干净的答案。

**问题 5：三个月能否做出可演示版本？**

技术上可以，但演示越完整，越像报告生成工具。

**最大风险**：类型上无法与已否决的“报告生成/核验”切割干净；即便切割，公开同功能产品已经存在。

## C18 多笔分期与消费信贷的真实成本和还款规划

**H1–H6**

| 门槛 | 判定 | 理由 |
|---|---|---|
| H1 | **通过（弱）** | 去掉“多笔现金流约束下的清偿顺序”，只剩年化换算；去掉“消费信贷”，年化换算没有特定场景。两端勉强成立，但“金融”端的厚度很低。 |
| H2 | **通过（弱）** | 有多笔分期的年轻人，决策是还款顺序和是否提前还。重复属性存在（每月还款），但单次决策的深度有限。 |
| H3 | **通过** | 可与强通用 AI 看截图算年化对比误差；“是否照规划执行、下月是否继续用”可观测。 |
| H4 | **不通过** | 候选卡自标“接近静态计算器”，这是准确的。C18 的核心是“把截图里的费率换算成年化 + 按利率排序”，多笔管理和跟踪执行是包裹在计算器外面的壳。盲评包明确否决“静态计算器”。C18 的“读真实账单”和“跟踪执行”是否足以让它脱离静态计算器的类型，取决于一个严格的标准：**它是否改变了决策本身，而不仅仅是呈现了决策所需的数字。** 按卡中描述，还款顺序是“按真实年化排序”的机械输出，现金流约束是输入条件，跟踪执行是一个提醒功能。这些是产品化增量，不是类型跃迁。 |
| H5 | **通过** | 本人和同学账单可获取，合成样本可构造。 |
| H6 | **通过** | 本人和同学是真实使用者，触达容易。 |

**H4 不通过。** 与 C17 同理，类型判定不是“有一点区别”就能通过。静态计算器加账单导入加提醒，仍然是计算器的一种产品形态，而不是一种新的金融决策系统。

公开信息进一步压缩了 C18 的空间：Tokeny 的“花呗分期与利率测算”skill 已经提供零依赖 IRR 计算器，明确写出“多笔分期并存时的清偿顺序（先清费率高的）”，并支持 agent 调用。Toolisland 的花呗分期计算器直接输出 IRR 真实年化，并做 3/6/9/12 期对比。C18 的“已知对手”栏写“待 GPT 查”，而公开的 IRR 计算和多笔排序逻辑已经是现成可得的。C18 剩下的增量是“读截图”和“跟踪执行”，前者是 OCR + 规则映射，后者是提醒功能，都不构成类型上的差异化。

**问题 1–3（简要，因 H4 已不通过）**

现有工具在计算端已经充分覆盖；多笔排序的逻辑也很简单。C18 的可证明结果（年化误差）在强通用 AI 面前可能没有显著优势。回来用第二次的理由在“提醒执行”上，但提醒本身是通用能力，不是金融科技壁垒。

**问题 4：面试价值**

消费金融岗位可能会认可“真实年化”的消费者保护视角，但面试官会敏锐地把它归类为“计算器 + 提醒”，难以展示系统设计或金融建模的深度。

**问题 5：三个月能否做出可演示版本？**

可以，而且会很快做出来。问题不在于“能不能做出来”，而在于做出来的东西在类型上与已否决类型的距离不足以通过盲评。

**最大风险**：类型上接近静态计算器，且公开工具已经覆盖 IRR 换算和多笔排序。

## 进入下一阶段实测的建议

**进入实测（4 张）：C08、C04、C01、C15。**

- **C08**：H1–H6 全部通过，差异化（条款可追溯 + 证据不足分流）在公开工具中不显著，负责人能触达真实保单使用者，面试信号（知识工程/证据意识）独特且可验证。最值得实测。
- **C04**：H1–H6 全部通过。风险明确（免费对账工具的存在），但“差错状态语义分类”是一个可被实测证伪或证实的窄点。如果能在实测中招募到小商户并展示差错定位增量，它是一个扎实的金融运营项目；如果招募失败，推翻条件干净触发，不浪费后续资源。
- **C01**：H1–H6 全部通过，技术判断力信号强。风险是 AP2/Coinbase 的窗口期，但“注入隔离 + 超时状态核验”是一个足够窄、足够可检验的增量。实测应该聚焦在：对照“平台原生全开”时，测试集是否真的能打出差异。
- **C15**：H1–H6 全部通过。竞争激烈，但“在转账流程内主动结构化询问”的位置如果能在产品形态上找到（哪怕是小程序 + 家属端通知的极简形态），仍然有普惠金融的产品信号。实测的核心问题不是模型效果，而是**老人是否真的在转账前用它**；如果两周内行为数据不成立，可以快速放弃。

**应直接淘汰：C17、C18。**

- **C17**：H4 不通过。类型上无法与已否决的“报告生成/核验”切割干净，且公开市场同功能产品不稀缺。
- **C18**：H4 不通过。类型上接近静态计算器，且 IRR 换算与多笔排序已有公开工具覆盖。

**C03 的处理**：不进入本轮实测，但不建议直接淘汰。它的 H1–H6 全部通过（H2/H6 偏弱），问题在于定位：它太容易被归入证券交易领域，与“第二个项目类型明显不同”的要求形成张力，且第二个真实用户的可获得性不明。如果 C08/C04/C01/C15 中有一张在实测早期被推翻，C03 可以作为替补，但前提是负责人能先找到一个非本人的模拟盘用户。
